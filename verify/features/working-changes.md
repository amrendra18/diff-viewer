# Staged and unstaged changes

## Sub-features

1. The tabs "Staged", "Unstaged", and "Commits" sit below the file list, each with a count. A dot beside Staged and Unstaged turns colored when the count is above 0. A bare repository shows only Commits.
2. Staged lists the last commit against the index. Unstaged lists the index against the working folder, plus untracked files as new files with an "untracked" tag. An untracked file over 200 KB, or one the app cannot read, reads "not counted" in place of its line counts; opening an unreadable one shows "This file could not be read". A file whose time changed but whose content did not is not listed.
3. Each tab has its summary ("Staged changes" or "Unstaged changes"), a panel with the count, what is compared, and a Refresh button, and the column labels "Last commit / Staged" and "Staged or last commit / Working folder" ("Not in git yet / Working folder" for an untracked file).
4. An empty tab shows "No staged changes" or "No unstaged changes" in the list and in the diff area.
5. The divider keeps its dragged position on all three tabs. `]` and `[` step through staged and unstaged files.
6. The window refreshes when it gets focus and when Refresh is clicked: counts, branch, newest commits, the file list, and the open file. While a refresh runs, the header's Refresh button has `aria-busy="true"` and its icon turns (unit test `refresh-click`). On the Commits tab, while a commit's file diff is on screen, a focus refresh does not reload that commit's file list or open file, because a commit's files do not change; the Refresh button does. The open file stays open while it is still listed. When its diff is unchanged, the page keeps the same rows, expanded lines, and scroll position. When its diff changed, the new rows keep the scroll position. When a refresh fails on the Staged or Unstaged tab, the diff area shows the error, and the next refresh that works shows the open file's diff again and removes the error. When git cannot list staged or unstaged files, their counts read "?" and the Commits tab keeps its commit list. An open commit file may show git's error while the index cannot be read, and the next refresh that works shows its diff again.
7. A merge conflict shows once, in Unstaged, with the chip "U" and a notice above the diff.
8. Bar 2 holds for the staged and unstaged lists: under 300 ms from the tab click to the painted list.

## How to get to it (user POV)

1. Open a repository. Click "Staged" or "Unstaged" below the file list.
2. Edit a file in another app and come back to the window, or click Refresh in the header or in the tab's panel.

## Driving it with scripts/verify

1. Run `scripts/verify fast --feature working-changes`. Add `--history-repo PATH` and `--file-repo PATH`, or set `DIFF_VIEWER_HISTORY_REPO` and `DIFF_VIEWER_FILE_REPO`, to also measure bar 2 for both lists on those repositories (opened read-only).
2. Bar 2 comes first, so its numbers exist even when a later focus step fails. On the fixture `practice`, and on each real repository given, it clicks Staged and Unstaged in turn, 5 times each, timing each click to the painted list or its empty line. `summary.json` holds `bar2StagedListMs`, `bar2UnstagedListMs`, and the same names with `HistoryRepo` or `FileRepo`. It then compares each tab's paths with git's own listing: `git diff-index --cached -M --ita-invisible-in-index HEAD` without conflicted rows for Staged, and `git diff-files --numstat` plus `git ls-files --others --exclude-standard` for Unstaged. `observations.workingListsMatchGit` holds the counts.
3. The harness builds its own practice copy under `fixtures-working/` and opens it. Tabs must read `Staged 2`, `Unstaged 2`, `Commits 12`. It drags the divider 80 px down.
4. Staged: files `M README.md`, `A staged-new.ts`; selection `Staged · 2 files`; summary "Staged changes" with "2 files ready for the next commit"; labels `Last commit`, `Staged`; one added row "Staged line."; the divider unchanged. `]` then `[` step to `src/staged-new.ts` and back.
5. Unstaged: files `M CHANGELOG.md`, `A todo.txt` with the tag `untracked`; `src/format.ts` (time changed, content not) is absent. `]` opens `notes/todo.txt` with labels `Not in git yet`, `Working folder` and the word "Untracked, new file".
6. Focus refresh: the harness edits lines 3 and 55 of `src/app.ts` on disk, moves the system focus away from the window and back, and waits for `Unstaged 3`. `notes/todo.txt` must still be open. It opens `src/app.ts`, expands the hidden lines, scrolls the diff to 250 px, and marks the panel element.
7. Unchanged open file: it appends a line to `notes/todo.txt` and refocuses. The list must show `+2−0` for `todo.txt`, and the open panel must be the same marked element, still scrolled to 250 px, with no hidden-lines bar.
8. Changed open file: it appends 60 lines to `src/app.ts` and clicks the header's Refresh. `app.ts` must read `+62−2`, the panel must be new, with 60 added rows, and the scroll must still be 250 px.
9. Unreadable untracked file: it makes the untracked `notes/todo.txt` unreadable (mode 000) and clicks the header's Refresh. `todo.txt` must read "not counted" in the list, and `src/app.ts` must stay open with its 60 added rows and no notice. Clicking `todo.txt` must show "This file could not be read". It restores the file's mode, appends a line to it, and clicks Refresh again. Once `todo.txt` reads `+3−0`, the diff area must hold `todo.txt`'s 3 added rows and no notice. `observations.workingUnreadable` holds both states. Then a refresh fails on the Unstaged tab: it makes the copy's `.git/index` unreadable (mode 000) and clicks Refresh, and the diff area must show "Git could not read this repository". It restores the mode and clicks Refresh again. The diff area must hold `todo.txt`'s 3 added rows and no notice. `observations.workingRefreshFailure` holds both states.
10. Clean: it runs `git reset --hard` and `git clean -fd` on its copy and clicks the panel's Refresh. Tabs must read `Staged 0`, `Unstaged 0`, `Commits 12`, with "No unstaged changes." in the list and "No unstaged changes" in the diff area. Staged then shows "No staged changes". Back on Commits, the divider is where it was dragged.
11. Refresh after an error on the Commits tab: with no commit chosen, it makes the copy's `.git/index` unreadable (mode 000) and clicks Refresh. The Staged and Unstaged counts must turn to "?", and the diff area must still show "Choose a commit" with no error. It restores the mode, writes a new untracked file, and clicks Refresh. Once Unstaged reads 1, the diff area must still show "Choose a commit". It then opens "Rework the app module" and `src/app.ts`, and repeats the same failure and recovery with a second untracked file. Once Unstaged reads 2, the diff area must hold the same change rows as before and no notice. During this second failure the open file may show git's error; only the recovery is checked.
12. Merge conflict: on its copy, it commits a change to `README.md` on `main` and a different one on a new branch, then merges that branch, which stops on a conflict. It clicks Refresh. Staged must show 0 files. Unstaged must list `U README.md` once, beside the two untracked files. Opening `README.md` must show the word "Unmerged, has a merge conflict", the notice "This file has a merge conflict. Left: your side before the merge. Right: the working folder, with the conflict markers.", and one `<<<<<<< HEAD` line on the right. It then runs `git merge --abort`, clicks Refresh, and expects only the two untracked files. `observations.workingConflict` holds what the page showed.
13. `observations.workingRefresh` holds the scroll position and panel identity before and after both refreshes. `observations.refocus` holds each focus try: the front app, `BrowserWindow.isFocused()` before and after, whether the page saw a `focus` event, and the time it took.

## Gotchas

1. Playwright emulates a page that always has focus, which hides real focus changes from the page. The harness turns that emulation off for the page (`Emulation.setFocusEmulationEnabled`), then calls `blur()` and `focus()` on the window in main, so the page gets the same `focus` event as after a switch from an editor. A try counts only when main reports `BrowserWindow.isFocused()` true and the page saw a `focus` event within 3 s. The harness makes up to 3 tries. When all fail, the failure names the front app and `isFocused()`.
2. The page skips a focus refresh within 1 s of the last one (`FOCUS_REFRESH_GAP_MS` in `src/web/renderer.ts`). The harness waits 1.2 s before each refocus.
3. A screen that locks during the run fails focus steps for a reason outside the app. When a journey fails with `loginwindow` in front, the run exits 3 with "the screen locked during the run" and runs no further journeys.
4. The harness focuses the app window, so keys someone types in another app at that moment reach the app. A Space scrolls the diff to its end; Space on the focused file re-opens it without its expanded lines. One injected key reproduces both. The harness therefore blocks the system's keys and pointer in every app window it launches (see the verify skill, Launch 8). A failed run keeps `traces/working-changes.zip`, `logs/working-changes-events.json`, and `screens/working-changes-failed.png`.
5. The unit tests in `tests/working-cases.test.mts` cover the git edge cases on throwaway repositories: no commit yet, merge conflict, `git add -N`, a file deleted on disk, a staged rename then edited, mode-only, submodule commits and a dirty submodule, symlinks, CRLF, tracked ignored files, untracked binary files, an untracked file over 5,000 lines (and a sparse 600 MiB one that answers "too large" without a full read), a nested repository, and `.git` left byte-identical where `git status` and `git check-attr` run.
